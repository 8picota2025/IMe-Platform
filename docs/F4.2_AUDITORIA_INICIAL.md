## 4. Flujos actuales

### 4.1 Comprabilidad / CTA

Regla vigente (código + commit `d163df4`):

> Producto con precio público > 0 y `disponible !== false` → carrito.  
> Sin precio → cotización.  
> Con precio y `disponible === false` → consultar disponibilidad.

Implementación central parcial:

- `src/lib/comercial.ts` → `getAccionComercial()`
- UI: `ProductoCard.astro`, `ProductoLanding.astro`, home
- Server: `crear-pago` recalcula precio; rechaza sin precio / `disponible=false` / stock insuficiente si `stock !== null`

**No hay** función única `isPurchasable()` que unifique stock, `gestionar_stock`, `stock_estado`, `fulfillment_mode`, bundles.

Umbral **$6.000.000 COP:** **no aparece en código ni tests**. No usar como criterio de comprabilidad.

### 4.2 Precio público

`resolvePrecioPublico()` (`format.ts`): oferta vigente o `precio_regular` + **IVA 19%** Colombia. Catálogo (`datos.ts`) expone ese valor como `producto.precio`. Checkout alinea con oferta/`precio_regular` + lista B2B.

### 4.3 Carrito → checkout → pago → pedido → stock

```text
Carrito cliente (localStorage + opcional guardar-carrito)
  → crear-pago (Edge): revalida disponible, precio, stock snapshot, cupón
  → crea pedido pendiente + URL Wompi/Stripe
  → webhook-*: valida firma, inserta eventos_pago (idempotente),
               claimPaidTransition (neq estado pagado), side effects solo si claim gana
  → notificar-proveedor / post-pago
```

**Stock:**

- Check no atómico en `crear-pago` (`cantidad > producto.stock` si stock no null).
- **No hay decremento de stock** en `post-pago`, webhooks ni fulfillments.
- **No hay reservas** con TTL.
- Race TOCTOU: dos checkouts concurrentes con 1 unidad pueden ambos pasar el check.

Idempotencia pagos: **sí** (`eventos_pago` + `claimPaidTransition`). Buena base; no cubre inventario.

### 4.4 Carrito abandonado

- `guardar-carrito`: email + items; rate-limit; **sin consentimiento**.
- `recordatorio-carritos`: envía email tras N horas; marca `recordado`; **sin verificar consentimiento/canal**.

### 4.5 Cupones

Infra técnica existe (admin + `crear-pago`). `COMPRAHOY` **no** está seeded/publicado en repo. Feature flag UI off por defecto.

### 4.6 Admin

Vistas: productos, cupones, reseñas, stock operativo parcial, proveedores, etc.  
**No existe** `/admin/compra-directa` ni vista equivalente dedicada a “stock físico / reservado / disponible + preview CTA”.

Roles: `is_admin([...])` + RLS; `service_role` solo Edge.

### 4.7 SEO / JSON-LD / reseñas

- `seo.ts`: Product+Offer solo con precio público; **sin** `aggregateRating` inventado (tests lo afirman).
- `Resenas.astro`: reseñas reales vía Supabase; no se inyectan en JSON-LD automáticamente (correcto si no hay aggregate).

### 4.8 Feed Google Merchant

**Ausente.** Ni `feed-google.xml` ni Edge `generar-feed-google`.

### 4.9 Recomendaciones

`match_productos` = similitud vectorial. Landing usa “relacionados”; no hay evidencia de “comprados juntos” basado en pedidos.

### 4.10 Bundles

No hay modelo ni seeds `kit-*`.

## 6. Riesgos de migración / operación

1. **Doble venta última unidad** (alto) — check stock sin reserva/lock.
2. **Publicar precios/stock en feed estático de build** (alto si se elige mal) — snapshot desactualizado.
3. **Activar más productos a checkout** sin inventario atómico (alto).
4. **Emails abandono sin consentimiento** (legal/comercial).
5. **Mutar `tipo_comercial`** para forzar buckets (prohibido por prompt; hoy CTA ya no depende de eso).
6. **Columna `requiere_invima` inventada** sin semántica → riesgo regulatorio.
7. **Bundles con SKUs inventados** → datos falsos.
8. Migraciones concurrentes con dropship `fulfillment_snapshots` reciente — revisar orden.
